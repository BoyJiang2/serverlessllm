# Runtime hook source audit (read-only, 2026-11-03)

Scope: inspected retained evidence, primary upstream source, and an explicitly authorized native SSH read-only host snapshot. No GPU, containers, hook invocation, sudo, installation, configuration edits, Git, or synchronization performed.

## Conclusions

1. The retained error identifies `createContainer hook #4` exiting with runtime/cgo pthread creation EAGAIN before the application. runc numbers hooks from zero and stops on the first failing entry. The fallback CDI list's fifth global hook is `disable-device-node-modification`; the failed OCI spec is gone, so that identification is a hypothesis, not historical proof. [runc Hooks.Run and Command.Run](https://github.com/opencontainers/runc/blob/v1.3.5/libcontainer/configs/config.go#L481-L577)

2. Actual create ordering matters. runc init runs CreateContainer during prepareRootfs, after parent-hook synchronization and chdir(rootfs), but before pivot/chroot. [rootfs source](https://github.com/opencontainers/runc/blob/v1.3.5/libcontainer/rootfs_linux.go#L171-L205) It precedes syncParentReady, application seccomp setup, and finalizeNamespace (which calls setupUser). Thus application UID and configured application seccomp do not describe this hook's execution credentials/filter. Existing inherited filters remain possible. [standard init](https://github.com/opencontainers/runc/blob/v1.3.5/libcontainer/standard_init_linux.go#L84-L175), [user switch](https://github.com/opencontainers/runc/blob/v1.3.5/libcontainer/init_linux.go#L295-L320)

3. runc applies the init cgroup before child setup, resets affinity against the cgroup cpuset, and applies configured cgroup resources at procHooks. It applies configured process rlimits later, at procReady. Therefore the hook inherits init's then-current cgroup, UID, affinity and inherited limits; a Docker Ulimits setting cannot alone establish the limits active during CreateContainer. The retained parent runc/shim snapshots both show UID0, Seccomp0, 10 threads and allowed CPUs 0-239, but neither snapshot is the failed hook itself. [process sequencing](https://github.com/opencontainers/runc/blob/v1.3.5/libcontainer/process_linux.go#L596-L615), [resource and rlimit sequencing](https://github.com/opencontainers/runc/blob/v1.3.5/libcontainer/process_linux.go#L743-L795)

4. EAGAIN does not uniquely diagnose PID exhaustion. Linux pids policy is hierarchical and returns EAGAIN at a limiting ancestor; RLIMIT_NPROC and global threads-max can also return EAGAIN. glibc additionally converts stack allocation ENOMEM and some thread creation ENOMEM to EAGAIN. Current host is kernel 5.15.0-91-generic and libc6 2.35-0ubuntu3.9. Upstream base sources explain semantics but do not establish the distro patch delta. [pids controller](https://github.com/torvalds/linux/blob/v5.15/kernel/cgroup/pids.c#L1-L25), [fork limits](https://github.com/torvalds/linux/blob/v5.15/kernel/fork.c), [glibc stack conversion](https://github.com/bminor/glibc/blob/glibc-2.35/nptl/pthread_create.c#L591-L600), [glibc creation conversion](https://github.com/bminor/glibc/blob/glibc-2.35/nptl/pthread_create.c#L792-L795). A CPU-only pids128 control succeeding with max events zero proves that control only; it neither attributes nor excludes the historical GPU-create environment.

5. Go's cgo path uses pthread_create with default detached thread attributes; Go1.26.0 retries EAGAIN 20 times before fatal error. This is an OS-thread creation failure, not a model-loader error. [cgo thread start](https://github.com/golang/go/blob/go1.26.0/src/runtime/cgo/gcc_linux_amd64.c#L48-L70), [retry loop](https://github.com/golang/go/blob/go1.26.0/src/runtime/cgo/gcc_libinit.c#L193-L212). Wide CPU affinity can influence Go scheduling/GC demand, but 240 allowed CPUs does not prove 240 OS threads or pids128 exhaustion.

6. Hook compiler is now verified from inline ELF buildinfo, without executing the hook: Go1.26.0, CGO_ENABLED=1, embedded NVIDIA commit ec7b4e2fa2caecad6d89be4a26029b831fe7503a/version1.19.0. Binary SHA256 is fb9e22c288346e9a99cfbef446a8495932073608aa9982628a750cacb129925c. This replaces the earlier unknown/compiler inference from runc. One precision gap remains: retained stack runtime.main at proc.go:216 calls makechan, whereas upstream Go1.26.0 places main_init_done = make(chan bool) at GitHub source line207; line217 is a throw statement. Do not claim exact line equivalence or silently attribute distro/build source deltas. The retained runtime.main→makechan→mallocgc→gcStart and absence of NVIDIA main frames support runtime startup failure before the hook's command action. [Go1.26 main](https://github.com/golang/go/blob/go1.26.0/src/runtime/proc.go#L194-L270). Evidence: work/runtime-buildinfo-proto.txt and independently decoded work/runtime-host-limits.json.

7. NVIDIA main builds CLI commands then runs them. The hypothesized disable-device-node-modification action reads host NVIDIA params and, when needed, writes a modified params file inside the container root. It is not equivalent to --version, and must not be executed as a diagnostic under this scope. [main](https://github.com/NVIDIA/nvidia-container-toolkit/blob/ec7b4e2fa2caecad6d89be4a26029b831fe7503a/cmd/nvidia-cdi-hook/main.go#L38-L84), [action](https://github.com/NVIDIA/nvidia-container-toolkit/blob/ec7b4e2fa2caecad6d89be4a26029b831fe7503a/cmd/nvidia-cdi-hook/disable-device-node-modification/disable-device-node-modification.go#L69-L109).
