# Native Kimi tokenizer: regex / special-ID source audit

**Verdict: native construction and one roundtrip pass; semantic parity does not pass.** This audit executed no container, tokenizer, model, GPU or checkpoint Python. It read the entire 13,462-byte official `tokenization_kimi.py` through native Windows SSH and parsed its AST locally. Source SHA256: `2ab1ffb6f5c4380758bd8d9752ff1041c09024182676a4311528fbdf92fb9599`. Selected inputs/line references are preserved in `runtime-native-config-source.json`, `kimi-tokenizer-reference-source.json` and `native-tokenizer-regex-audit.json`.

## Mistral warning: trigger is overbroad

TF5.5.1 `tokenization_utils_tokenizers.py:474–483` runs the check for vocab_size>100000 with a pretokenizer. `_patch_mistral_regex:1293–1294` treats offline as local. It reads the top-level config and only performs the non-Mistral early return inside the branch requiring a nonempty top-level `transformers_version<=4.57.2` (:1321–1334), or returns for a version>4.57.3 (:1335–1336). This snapshot has `model_type=kimi_k25` but no top-level transformers_version (the nested text_config version4.56.2 does not count). Thus :1338 marks `mistral_config_detected=True` and :1346–1351 emits the Mistral message. It does not compare this Kimi regex with any official Kimi regex. The Mistral attribution is a false positive from those conditions; this does not establish that tokenization is correct.

Do not apply `fix_mistral_regex=True`. Its replacement pattern (:1357–1359) is not Kimi's pattern: among other differences, it splits numbers singly whereas Kimi uses groups of1–3, and it has no separate Han branch.

## Independent, substantive differences

Official `tokenization_kimi.py:52` defines a Han-specific branch `[\p{Han}]+`, followed by separate upper/lowercase Unicode branches excluding Han; contraction suffixes attach to those branches, then `\p{N}{1,3}` and whitespace/punctuation branches. It passes `self.pat_str` to `tiktoken.Encoding`. `tokenizer_config.json` contains no pat_str/pattern/regex override.

TF's SentencePiece-failure fallback `tokenization_utils_tokenizers.py:278–283` calls `TikTokenConverter(vocab_file=...,extra_special_tokens=...)` without a pattern argument. `convert_slow_tokenizer.py:1906` defaults to the generic contraction / `\p{L}+` regex, and :1958–1962 installs it into the backend Split+ByteLevel pretokenizer. These pattern strings differ; actual backend serialized state and a counterexample remain to be measured. The warning is not evidence of the exact pattern; source analysis identifies the predicted fallback pattern independently.

**Already observed special-ID mismatch:** the runtime returned PAD163606, while this snapshot's tokenizer_config explicitly assigns `[PAD]` to163839 and `[UNK]` to163838; it assigns `<think>` to163606. Native len163607 versus basevocab163584 shows only23 added tokens. The official tokenizer constructs256 reserved slots at IDs163584–163839, filling listed names at their declared positions and remaining slots with `<|reserved_token_ID|>`; its tiktoken n_vocab should be163840. BOS/EOS163584/163585 happen to agree, but that does not rescue the PAD mismatch. Need compare all23 named mappings and reserved slots rather than speculate a tokenizer fix. Generic backend addition enumerates configured token strings and can compact sparse IDs; exact runtime added-vocab dump will locate every mismatch.

Config vocab163840 alone need not equal a tokenizer's populated vocabulary size in every model; here the official source's explicit256-reserved-slot construction plus declared PAD ID makes the specific mismatch concrete. One successful encode/decode roundtrip only establishes invertibility for that sample, not expected model IDs.
