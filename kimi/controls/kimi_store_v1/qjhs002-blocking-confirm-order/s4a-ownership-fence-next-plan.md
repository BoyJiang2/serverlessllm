# Next ownership-fence plan: minimal scope and reviewable choices

Design/source review only. No candidate execution, deployment-source edit, build, GPU, Store, SSH, Git or sync. c947 remains rejected. This plan grants no runtime authorization.

## Recommendation for the next action

Keep the S4a component candidate and the rejected S5 patch separate. First review a small CPU-only model of admission/drain ordering against the exact existing interfaces, plus a concrete same-container parent/server/client failure barrier. Do not implement a general SDK cancellation subsystem merely to make the 8MiB component readback possible. Choose explicitly whether the next milestone is bounded S4a happy-path evidence with failure containment, or SDK-wide S5 eager failure ownership. They have different completion claims.

Existing ConfirmModel success is already sufficient for the normal load/copy/close path. Do not add another success RPC or change its exception behavior. The actual missing contract is an idempotent release fence after an ambiguous submission, including a submission that reaches the server after the release request.

## Exact existing facts and limits

client.load_into_gpu collapses grpc errors into False. LoadModelAsync schedules std::async work and returns before native copy completion. False/exception cannot distinguish rejected-before-borrow from response-lost-after-acceptance. Generic INTERNAL, CANCELLED, socket close, CPU unload, or absence of a replica at one instant is not proof of no future borrow.

Exact model.cpp SHA256 6f8b64645763a1e336b77f27c8a301bb45e84b545e38858e8374f80091a84509: ToGpu joins dispatch/copy futures, then attempts all IPC closes while holding Model mutex, marks INTERRUPTED on close failure, and notifies. WaitInGpu uses that mutex and returns zero only for LOADED; successful ConfirmModel therefore proves completion and successful IPC close for this replica. INTERRUPTED does not say whether all handles closed. Unknown replica WaitInGpu waits without a deadline. FreeHost waits currently registered LOADING replicas and can miss a not-yet-registered async task.

GetDevicePtrsFromMemHandles currently occurs before Model::ToGpu registers its replica. ToGpu can return early for uninitialized/duplicate replicas. This makes registering a tombstone only inside Model::gpu_replicas_ too late. Ownership of all successfully opened handles also needs explicit native cleanup on every return/exception, not just the successful ToGpu close loop.

## Smallest defensible SDK release-fence protocol, if S5 is pursued

Reuse the existing UnloadModel RPC with DEVICE_TYPE_GPU and replica_uuid. Those fields and response.code already exist in storage.proto; server.py currently rejects GPU unload, so this requires new semantics and native binding, but no wire-schema/new-RPC change is inherently necessary. Add an explicitly named client release/drain method rather than pretending CPU unload is the fence. Require a successful RPC and explicit successful code. A deadline/transport failure is UNKNOWN, never permission to free. A lost successful reply can be retried idempotently with the same UUID.

1. Store admission owns records keyed by (model_path, replica_uuid), with a lock shared by GPU admission and release-fence requests. On load admission, create the record synchronously before enqueueing any task or opening any IPC handle. Reject duplicate loads for the same UUID. This record must encompass all work from handle-open through final close; a Model replica alone is insufficient.
2. A release request atomically seals that key against future admission. If the load has not arrived, keep a tombstone and acknowledge no borrower; any delayed original load must then be rejected before opening IPC. If admission won the race, seal it and wait for that admitted task and every handle-close attempt to finish. Do not hold the admission lock while joining tasks that need it.
3. A task may run to completion rather than being actively cancelled. Waiting plus outer bounded timeout is simpler than adding cancellation through dispatcher queues. Active cancellation is not required for correctness of the fence; it would need additional queue-wakeup and join semantics. If completion does not occur within the existing guard, fence fails/UNKNOWN and containment takes over. Never extend GO25 to rescue it.
4. Track borrower release separately from tensor-copy success: all opened handles closed is RELEASED even if copy failed; an IPC close failure is NOT_RELEASED. No-handle-open is also RELEASED. Every partial handle-open, early return, worker exception and ToGpu failure must feed this outcome. Native RAII may centralize importer-handle closure, but do not double-close existing handles or duplicate cudaFree exporter ownership.
5. Return a release-success ACK only after the sealed record has no active/open/late borrower and every opened handle is confirmed closed. Keep the tombstone until this Store lifetime ends; do not erase it immediately after ACK and permit a late request. For this one-attempt component, no tombstone eviction subsystem is needed.
6. Client keeps exporter owner alive from before handle export through submit, confirm or release fence. Pre-submit failures can free immediately. After any possibly submitted request, free only on successful ConfirmModel or successful release fence. A fence error/deadline requires preserved owner until isolated server termination is verified. Do not rely on exception traceback lifetime or let a local dictionary naturally destruct on the error return. Preservation/handoff must be explicit in the existing component/SDK contract.

Likely minimum code scope: checkpoint_store.h/.cpp admission record and drain method; existing Python/C++ binding file exposing it; model.h/.cpp or existing importer helper to provide unambiguous close outcome and cover early/partial failures; server.py GPU UnloadModel branch; client.py bounded release method; torch.py explicit exporter ownership handoff and error preservation. Inspect the exact binding/header before committing to line-level changes. storage.proto can remain unchanged if the above semantics fit existing fields. No new codec, loader, converter, service or deployment framework. This is larger than the rejected one-file change because async admission and importer closure are native facts.

A boolean submitted flag alone is insufficient: delayed server admission remains possible, and owner destruction on exception still frees. Adding a confirm retry alone is insufficient: unknown UUID may wait forever, failed close is not a fence, and another lost reply stays ambiguous.

## CPU regression orders required before any native change is accepted

Use events/barriers in a deterministic mock of the actual admission and owner API, not sleeps or fake GPU success claims. Cover: release-before-load arrival (late load rejected without open); admission-before-release but worker registration delayed; open-before-release with copy running; copy failed but close succeeded; partial open followed by failure; close failure; reply lost after admission; reply lost after fence success then idempotent retry; duplicate submit; owner retained while original exception/traceback lives and after exception handoff; cleanup error preserving primary exception; no-submit handle failure; normal success retaining final alias until its destruction. Assert no exporter free while any importer borrow is active or may still be admitted. A fake that simply returns False and demands immediate free encodes the defect. These tests prove ordering logic only, not CUDA/native release.

## Narrow same-container S4a containment option

A full SDK fence is not logically necessary to obtain S4a successful component readback plus successful-path eager final-alias release: existing ConfirmModel success already supplies the needed success fence. Those results must leave S5 ambiguous-failure ownership pending. One separately reviewed attempt may retain this limited claim only if its failure lifecycle is explicitly contained; current component finally by itself is not that lifecycle protocol.

Use the already intended parent, official server process and client process in one guarded container. Before any client error can cause owner destruction or client exit, a cooperative failure barrier must preserve exporter memory, notify the parent, stop the owned server, wait for its verified PID/starttick exit, then allow client cleanup/exit. Parent must stop server before terminating client on deadlines as well; simultaneous container kill alone does not prove this order. Pipe EOF/client crash must not be labelled a successful barrier. Server graceful stop can consume up to five seconds and belongs inside GO25; all fallback cleanup remains inside cleanup65, release60 and full180.

This can establish that the importer process is gone before cooperative exporter release and that final teardown clears the isolated processes. It cannot establish eager error-path cudaFree, native importer close success, safe library-level behavior for other callers, or crash-free exporter lifetime. An uncaught native failure or allocation owner freed inside a callee before the cooperative barrier is not repaired by a later parent stop. In particular, RestoreTensors owns/frees on its own exception unwind; moving it around without native importer-lifetime reasoning is not an all-failure repair. Keep that limitation explicit rather than expanding a happy-path S4a claim to S5.

For successful S4a, preserve the candidate's in-process retained packed-alias hash, driver allocation held until last alias, and driver release after last alias before server teardown. Process exit and 60s quiet observation are additional containment evidence, not substitutes for that eager alias proof. For any failed attempt, retain FAILED_RETAINED and the exact failure stage; do not manufacture successful ownership evidence from teardown.

Next reviewable deliverable should therefore be one small CPU-only protocol regression/design diff for the chosen scope, with exact owner-retention and server-before-client barriers stated, then independent review. Do not deploy c947 or start a new GPU attempt while that choice and the concrete GO25 subphase cutoffs remain unreviewed.

## Narrower blocking-only supplement (authoritative next step)

A smaller change than the SDK-wide fence above closes the specific RestoreTensors-before-confirm hazard for this bounded blocking S4a attempt. It does not close general SDK error ownership.

In exact torch.py, give load_dict_non_blocking a private optional _confirm_before_restore=False parameter. Public nonblocking callers retain the default behavior. Blocking load_dict passes True and removes its current outer duplicate confirmation. Inside the existing flow, after successful GPU submission and before restore_tensors, conditionally call the existing client.confirm_model_loaded(model_path, replica_uuid). Restore only after it returns successfully. Keep the same official load/confirm/restore APIs and exactly one successful confirmation RPC. No new native code, RPC, Proto, codec or framework is needed for this narrow ordering change.

Why this is sound: successful ConfirmModel reaches WaitInGpu and acquires the mutex after ToGpu finishes dispatch/copy futures and its entire IPC-close loop. LOADED cannot be observed through that mutex before the close loop finishes; close failures make INTERRUPTED and cannot produce a successful confirm. Thus when RestoreTensors acquires native allocation ownership, the server has already released its IPC borrow. RestoreTensors C++ exception unwinding can then cudaFree without the identified active-importer hazard. Python argument-conversion failure before C++ entry leaves raw allocation unowned but does not create early free; this is containment-only, not eager-cleanup proof.

If submit or confirmation fails, restore is not reached: raw CUDA pointers have no owner/destructor and remain allocated in the still-live client context. The component failure barrier must stop/reap the owned server before allowing client exit, preserving the original exception. Run that barrier before destructive finally actions on any attempted-load primary error. Failed confirmation is not an eager-free success. Do not introduce a raw-pointer cudaFree in this path. Nonblocking original pre-restore failure gap remains pending.

Minimum actual change scope for this route: official torch.py ordering/private flag; existing component finally coordination hook; the already intended same-container parent/server/client orchestration; focused CPU AST/mock tests. The bounded parent timeout must stop server before client; preserve GO25/cleanup65/release60/native140/full180. A server-stop timeout, failed reap, missing barrier ACK or unexpected client exit is FAILED_RETAINED, not permission to claim ownership success. Cooperative Python failures can be covered; arbitrary SIGKILL/client crash cannot be turned into an ordering guarantee by Python barriers.

CPU ordering tests should execute both actual function ASTs: blocking success requires submit -> confirm -> restore and exactly one confirm; submit False/transport failure and confirm exception require restore never called and context/allocation retained until simulated server-reaped barrier; restore exception requires confirm success occurred before its modeled native RAII free; nonblocking default retains its original no-confirm-before-return contract; original exception survives barrier/cleanup errors. No tests should demand eager free on ambiguous confirmation. Also retain success last-alias lifetime and primary-cleanup ordering tests. Native runtime proof still needs separately approved execution.

Review verdict for this design: ACCEPTABLE_TO_IMPLEMENT_AND_CPU_REVIEW within the above narrow scope; no execution authorization. This closes the source-proven blocking callee-premature-free ordering hazard, while leaving S5 general eager failure cleanup and nonblocking semantics explicitly unresolved. The earlier full release-fence protocol is an optional broader S5 route, not a prerequisite invented for this narrow change.
